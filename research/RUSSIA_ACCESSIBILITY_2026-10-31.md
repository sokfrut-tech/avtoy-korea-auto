# AVTOY KOREA — исследование доступности для России
Дата: 2026-10-31
Issue: https://github.com/sokfrut-tech/avtoy-korea-auto/issues/16
Ветка: research/russia-accessibility-migration

## Статус
Исследование начато. Production не менялся. Это предварительный технический отчёт, не разрешение на миграцию.

## 1. Подтверждённая инфраструктура
- Cloudflare Worker: avtoy-korea-auto.
- Публичная точка входа: https://avtoy-korea-auto.sokfrut.workers.dev/
- Один Worker обслуживает frontend, POST /api/request, Telegram webhook /telegram/webhook, каталог/отзывы и медиа.
- KV binding REVIEWS: namespace ID 302a622dc2514025b2118c8f3216beac.
- README и wrangler.toml подтверждают эту конфигурацию.
- Пользователь подтвердил, что после исправления KV binding заявка с сайта дошла в Telegram.
- Поэтому миграция только HTML неприемлема: API и webhook тоже должны быть доступны.

## 2. Причина проблем в России — сильная гипотеза
Cloudflare Support, документ “Potential disruption of services for Russian users”, обновлённый 2026-08-24, сообщает о систематическом ограничении трафика к Cloudflare-защищённым сайтам российскими ISP примерно до 16 KB на соединение. Cloudflare прямо указывает, что это не ошибка конфигурации Cloudflare и что провайдеры применяют ограничение на своей стороне.
Источник: https://developers.cloudflare.com/support/troubleshooting/general-troubleshooting/service-disruption/

Cloudflare Blog (2025-06-26) описывает аналогичную проблему с 2025-06-09 и объясняет, почему загрузка веб-страниц ломается при ограничении передачи около 16 KB:
https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet/

Это объясняет симптом, но для конкретного сайта требуется доказательная проверка с российских сетей. Не утверждать, что причина окончательно установлена без этих тестов.

## 3. Предварительная гипотеза решения
Рассмотреть размещение сайта и backend на российской инфраструктуре с публичным IP и DNS/TLS, не проксируемыми через Cloudflare для посетителей из России. Варианты для сравнения:
- Beget VPS/VDS: серверы в РФ и Казахстане; официальная страница: https://beget.com/ru/vps
- Timeweb Cloud: официально перечисляет ЦОД в Москве и Санкт-Петербурге: https://timeweb.cloud/docs/nashi-data-centry
- Timeweb shared hosting может быть дешевле, но пригодность для текущего backend/Telegram webhook нужно проверить: https://timeweb.com/ru/services/hosting/

Не выбирать провайдера до сравнения сетевой доступности из РФ, доступности Telegram API, стоимости, резервного копирования и возможности развёртывать Node-compatible runtime. Не покупать услуги.

## 4. Обязательные технические проверки
1. Получить реальные пробы из нескольких независимых сетей РФ (домашний интернет и мобильные операторы, желательно Москва/Санкт-Петербург и другой регион).
2. Для каждого теста сохранить: DNS A/AAAA, TLS handshake, HTTP status/headers, время до первого байта, загруженный объём, точку обрыва, полный/частичный HTML и загрузку JS/CSS/API.
3. Сравнить тот же URL из Германии и других контрольных сетей.
4. Проверить отдельно workers.dev, путь /, /api/cars, тестовый POST /api/request (только с безопасным тестовым контентом и без рассылки реальным администраторам), /telegram/webhook health behavior.
5. Проверить, не создаёт ли проблема сам сайт: крупный HTML/JS bundle, внешние CDN/шрифты, mixed content, ошибки JS.
6. Не отправлять тестовые сообщения реальному Telegram-боту и не менять webhook без согласования.

## 5. Архитектура миграции — обязательный охват
- Frontend и все статические ресурсы.
- POST /api/request и доставка заявок каждому администратору в личный Telegram.
- Telegram webhook, команды бота и ответы клиентам.
- Каталог автомобилей и импорт Telegram media_group.
- Модерация отзывов, публикация фото/видео.
- Хранилище заявок, статусов, отзывов и медиа.
- План экспорта/import KV с сохранением ключей, значений, TTL и проверкой количества/контрольных сумм.
- Секреты переносить только через секретное хранилище выбранного хостинга, не через GitHub-файлы/логи.

## 6. Безопасный порядок внедрения
1. Зафиксировать production commit и сделать резервную копию кода и данных.
2. Создать тестовое окружение на выбранном хостинге без влияния на текущий Worker.
3. Адаптировать runtime/API и покрыть тестами.
4. Перенести копию данных и проверить целостность.
5. Прогнать end-to-end тесты формы, каталога, отзывов, медиа, бота и webhook.
6. Получить реальные подтверждения доступа из нескольких сетей РФ.
7. Только после отдельного разрешения владельца — согласованно переключить домен/webhook.
8. Держать Cloudflare Worker и исходные данные как rollback до подтверждения стабильной работы.

## 7. Открытые вопросы / блокеры
- Есть ли собственный домен AVTOY KOREA и кто управляет DNS?
- Есть ли доступ к реальным тестерам/сетям в России для сетевых проб?
- Допустим ли небольшой ежемесячный бюджет на VPS? Без оплаты нельзя запустить независимую инфраструктуру.
- Есть ли подключённый Claude исполнитель? На данный момент фактический доступ к Claude из этого рабочего окружения не подтверждён; нельзя заявлять, что он участвовал.
- Текущий репозиторий должен быть проверен на полный список маршрутов, KV ключей, внешних зависимостей и тестовых workflow до реализации.

## 8. Решение на текущем этапе
Не менять production. Сначала выполнить диагностику, инвентаризацию backend и сравнение хостингов. При подтверждении Cloudflare ISP throttling наиболее перспективен отдельный российский origin/VPS с прямым DNS/TLS, а Cloudflare оставить для прежнего адреса/резервного контура, не направляя российский трафик через Cloudflare proxy.
